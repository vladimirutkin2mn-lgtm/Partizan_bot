# Partizan — автономный кандидат характера без смены писателя

Аудит `Partizan_generation_audit_2026-10-30.md` показал, что первая
сохранённая v17-инструкция многократно превращает **манеру** в **тему**
(границы, контроль, правила, верификация и т. п.). При этом текущий writer
достаточно последовательно исполняет профиль. Значит первым чистым
экспериментом должен быть **новый характер на неизменном v17 writer**,
а не изменение всех промптов сразу.

## Бесплатный запуск для существующего проекта

На уже подтверждённом продукте, после проверки PR #586:

```bash
python -m app.voice_challenger_bootstrap \\
  --project-id PROJECT_UUID --product-id PRODUCT_UUID
```

Без параметров выполняется только чтение. Отдельная команда:

```bash
python -m app.voice_challenger_bootstrap \\
  --project-id PROJECT_UUID --product-id PRODUCT_UUID --reserve-only
```

создаёт одну идемпотентную **неоплачиваемую** задачу в durable DB.
Она не генерирует текст, не переключает активный характер и не
инициирует AutoResearch без отдельного budgeted runner. CLI ещё не
зарегистрирована в cron и не включена в production workflow.

## Новый внутренний API

`VoiceProfileService.reserve_challenger(project_id, product_id, product_data)`:
- выполняет **ноль вызовов LLM** и ничего не публикует;
- требует активный исходный характер и неизменившийся product source;
- создаёт идемпотентную версионированную задачу `AUTORESEARCH`;
- хранит ссылку на immutable parent voice и ожидаемую ревизию назначения;
- не редактирует базовый профиль, не меняет champion/author assignment.

`VoiceProfileService.generate_reserved(..., allow_llm_call=True)` может
после **отдельного бюджетированного разрешения оператора** создать
одну независимую кандидатскую версию. Новая версия помечается
`CHALLENGER_UNREVIEWED`. При изменении продукта или назначения
генерация завершается **до вызова модели**. Если платный вызов имел
неизвестный/некорректный результат, автоматических повторов нет.

Промпт v3 извлекает характер автоматически из подтверждённых данных
о продукте и аудитории; пользователь его не настраивает.
Модель не должна назначать модераторскую повестку по названию категории.
Примеры принимаются только на реальных поверхностях `CHANNEL_COMMENT`,
`GROUP_REPLY`, `STANDALONE_POST`; synthetic examples отдельно от
style_instruction. Публикационная policy остаётся независимой.

## Чистая проверка до переключения

1. Экспортировать сохранённый product source и exact writer config
   из отдельного бесплатного PR #586, проверить их качество.
2. После отдельного ограничения расходов создать **ровно одного**
   кандидата (не активировать).
3. Выбрать 3–6 допустимых сохранённых постов, в том числе GROUP_REPLY
   если он подтверждён. Запрет profile promotion в Bizarre — отрицательный
   policy-case, не положительный маркетинговый кейс.
4. Заморозить модель, reasoning, sampling, max output tokens, system
   prompt, conversion brief и target text. В writer менять только
   version/content hash и разрешённые style-поля.
5. Оценить blind pairwise готовность оставить сообщение без правок,
   социальную уместность, незаученную позицию и запреты на рекламу.
   Rationale writer не использовать как judge.
6. Только после отдельного успешного анализа рассматривать ручное
   promote, canary и дальнейший AutoResearch.

**В этом PR нет оператора для платного запуска, scheduler, auto-promotion
или Telegram send.** Нынешний v17 baseline остаётся активной тестовой
версией, производственный writer flag не меняется. Отдельный эксперимент
с инструкцией writer v17.1 находится в другой незавершённой ветке и
не должен смешиваться с этим тестом.

Схема базового `VoiceProfileDraft` остаётся совместимой с ранее
сохранёнными v17 профилями. Более строгая проверка synthetic examples
применяется только к новым кандидатам после единственного model call,
чтобы исторический Moderation note можно было прочесть как evidence.

## Реальная проверка источника 31 октября

Бесплатный production run `41122914596` подтвердил, что исходная
карточка FemDom содержит метаданные рекламного актива, общий market,
тестовый бюджет и ссылку, но не содержит отдельно сформулированных
`known_audience`, `use_cases`, `product_type` и
`problem_or_desire`; `value_proposition` буквально дублирует
`description`. Нельзя автоматически принимать такой asset/campaign
brief за подробное описание ценности продукта. Конкретный тип
продвигаемого предложения в источнике остаётся неоднозначен.

Поэтому на этом источнике добавлен **readiness gate**: бесплатный
`app.voice_challenger_bootstrap` возвращает
`PRODUCT_UNDERSTANDING_INSUFFICIENT` с кодами недостающих измерений.
Он не создаёт ни candidate job, ни расходы. Тот же фильтр действует
внутри `reserve_challenger` и непосредственно перед возможным
LLM-вызовом, включая старые ранее зарезервированные кандидаты.
Исторический baseline остаётся доступным для чтения и исследования.

Не нужно заставлять клиента вручную описывать характер.
Требуется улучшить автоматическое понимание **самого продукта** из
доступного источника или уточнить только недостающие сведения о
ценности/аудитории в штатном product understanding. Не подставлять
предполагаемую AI-персону или другую бизнес-модель без подтверждения.

Также обнаружено, что production writer использует task-specific
`gpt-6.1-sol` с `medium` reasoning, а старый девятитекстовый пилот
выполнялся на `gpt-5.6`. Для нового сравнительного эксперимента
обязательна одинаковая разрешённая конфигурация для обеих сторон.
