## Boundary

Telegram client-owned publishing is intentionally separate from both Telegram research and the existing Telegram Bot execution adapter.

```text
research-only operator session
        -> SEARCH / evidence only

customer-owned Telegram user session
        -> explicit customer connection
        -> DRAFT / approval
        -> bounded PUBLISH
        -> receipt / observed provider signals

Partizan-owned Telegram bot identity
        -> separate execution adapter and permissions
```

Research credentials can never satisfy client-owned publishing readiness. A Telegram Bot token can never be treated as a connected customer user account.

## Fail-closed runtime configuration

The customer user session is never configured as an environment variable. It is generated by the authenticated customer login flow and encrypted at rest with the existing provider-secret encryption boundary.

Application-level publishing transport is independently gated:

```text
TELEGRAM_CLIENT_PUBLISH_PROVIDER=unavailable
TELEGRAM_CLIENT_PUBLISH_PUBLIC_READY=false
# TELEGRAM_CLIENT_PUBLISH_API_ID=
# TELEGRAM_CLIENT_PUBLISH_API_HASH=
PROVIDER_SECRET_ENCRYPTION_KEY=...
```

To make the customer connection flow operational in a controlled environment all four readiness conditions must be true:

1. provider is `telethon`;
2. `TELEGRAM_CLIENT_PUBLISH_PUBLIC_READY=true`;
3. app-level Telegram API ID/hash are configured;
4. encrypted provider-secret storage is configured.

Production remains unavailable by default.

## Customer connection lifecycle

Authenticated workspace routes:

- `POST /customer/workspace/{project_id}/telegram/connection/start`
- `POST /customer/workspace/{project_id}/telegram/connection/confirm`
- `GET /customer/workspace/{project_id}/telegram/connection`
- `DELETE /customer/workspace/{project_id}/telegram/connection`

The browser submits a phone number to start Telegram's login challenge and then submits the Telegram login code. If Telegram requires two-factor authentication, the confirmation route returns `PASSWORD_REQUIRED` and accepts the password on the next confirmation request.

The browser never receives:

- a Telethon `StringSession`;
- Telegram's phone-code hash;
- the app API hash;
- the submitted login code;
- the submitted two-factor password.

Temporary login material, including the phone number, code hash and temporary session, is stored only as one encrypted provider secret with a ten-minute challenge lifetime. On successful authorization the temporary secret is deleted and the final authorised `StringSession` is stored under a separate encrypted customer-Telegram session reference.

The safe connection view contains only Telegram user ID, public username/display name and connection timestamps. Disconnect removes the stored authorised session reference.

## Publish boundary

Authenticated publish route:

```text
POST /customer/workspace/{project_id}/telegram/actions/{action_id}/publish
```

A network publish is rejected unless all of the following hold:

- the feature-level publishing readiness gate is open;
- the DistributionAction belongs to the customer's project/product;
- platform is Telegram;
- action type is `COMMENT`, `REPLY` or `STANDALONE_POST`;
- action status is already `APPROVED`;
- the project explicitly selected `CLIENT_OWNED` publisher mode for Telegram;
- an authorised encrypted customer Telegram session exists;
- approved content is non-empty and at most 4,000 characters;
- the target is a public `https://t.me/...` surface.

Standalone posts require a public community URL. Comments/replies require a concrete public message URL. Private invite URLs are rejected.

The production Telethon transport resolves the target and refuses anything that is not a Telegram `Channel`/megagroup-style community entity before calling `send_message`. It exposes no join, invite, participant-enumeration or direct-message operation.

## Approval and automation

Every client-owned publish currently requires an already `APPROVED` DistributionAction. Phase 3 does not add Telegram to autonomous channel execution. This preserves an explicit customer/operator approval boundary for the first publish and every publish in this initial implementation slice.

Per-project autonomous Telegram publishing remains unavailable until a later Phase 3 slice adds an explicit automation approval state and proves its readiness controls.

## Frequency and duplicate guardrails

The service currently enforces conservative hard limits per customer project:

- no duplicate normalized content to the same target for 24 hours;
- at least 60 seconds between confirmed publishes;
- at most 10 confirmed client-owned Telegram publishes per 24 hours.

Only successful remote publishes enter this history. A failed attempt leaves the DistributionAction `APPROVED` so a retry remains explicit.

## Receipts and provider signals

On success the receipt records non-secret execution evidence:

- remote Telegram peer ID;
- remote message ID;
- reply target message ID when applicable;
- remote execution URL;
- provider-confirmed publication timestamp;
- connected Telegram user ID;
- action type and public target username.

Known provider restrictions are mapped to stable safe codes rather than raw exception strings. Examples include write-forbidden, account-restricted, slow-mode, rate-limit and inaccessible-community signals. A failed or restricted publish does not mark the DistributionAction executed.

The customer session, API hash, login code, two-factor password and provider exception text are never persisted in the receipt.

## Acceptance status for #251

This implementation is intended to prove the following in CI before any production activation claim:

- encrypted customer session lifecycle with browser/log secret isolation;
- independent research-vs-publish readiness;
- explicit action approval before network publish;
- public-community-only target validation;
- remote ID/timestamp/status receipts;
- observable provider restriction signals;
- duplicate/frequency/spam guardrails;
- no join/invite/participant-enumeration/mass-DM path.

Still required before #251 can close:

- complete channel-native drafting from selected opportunity/context where the product does not already provide approved copy;
- explicit per-project Telegram automation approval/readiness if automation is to be offered;
- post-publish removal/result observation where Telegram exposes it;
- at least one real production customer-owned publish and result capture on an exact deployed release.

## Production gate

A green mocked/integration test is not production acceptance. `TELEGRAM_CLIENT_PUBLISH_PUBLIC_READY` must remain false in production until a deliberate production verification plan is approved. Phase 2 issue #250 also remains independently open until its postponed real research evidence run is completed.
