# FemDom: проверка старой базы Telegram, а не новый платный поиск

## Что проверяем

Старые найденные группы могут находиться в двух местах:

- `telegram_community_registry` — новый канонический реестр;
- `audience_distribution_map` — результаты **предыдущих** прогонов,
  включая возможности, найденные до появления нового реестра.

`app.historical_telegram_community_audit` только читает обе базы,
объединяет публичные сообщества по `@handle`, считает покрытие и затем
проверяет **не более 12** сохранённых публичных сообществ через
`TelegramResearchConnector.inspect_known`.

Это важное отличие от запуска Discovery: **Telegram contacts.Search не
вызывается, OpenAI/платный веб-поиск вообще не используется.**

## Что показывает результат

- `inventory`: число записей старого реестра, исторической карты,
  уникальных публичных сообществ, пересечения баз, неподходящих
  приватных ссылок и подтверждённой пригодности аудитории;
- `communities[].sources`: откуда мы знаем конкретную группу;
- `communities[].inspection`: удалось ли реально обновить её;
- `fresh_posts`: конкретные публичные URL и дата сообщений за
  последние семь дней (если наш read-only transport их получил);
- `fresh_keyword_match_count`: сколько свежих сообщений содержат
  слова из сохранённого профиля продукта. **Это только диагностический
  сигнал**, а не семантическая оценка качества;
- `selected_target_url`: какую публикацию выбрал бы текущий
  `select_telegram_participation_target`;
- `selected_target_keyword_match`: соответствует ли выбранный системой
  новейший пост хотя бы одному продуктному слову;
- никакая группа/публикация не объявляется доступной для отправки
  без отдельной проверки полномочий и согласования.

## Известное ограничение текущего алгоритма

Существующий `CommunityFirstTelegramDiscoveryAdapter.refresh_registered`
обходит по три старые группы за один запуск и читает обычно четыре
последних сообщения.

`select_telegram_participation_target` выбирает **самое новое**
сообщение, а не обязательно наиболее релевантное. Таким образом,
подходящая по теме группа и свежий пост сами по себе ещё не
подтверждают, что выбранный пост подходит для комментария. Этот аудит
специально фиксирует такой сценарий (есть регрессионный тест), не
ослабляя правила выбора и не публикуя старые посты.

## Как воспроизвести

Только инвентаризация, без подключения к Telegram:

```bash
python -m app.historical_telegram_community_audit \
  --product-id 52d7e59e-5ac5-4363-b829-c93e33e48272 \
  --inventory-only
```

Ограниченная проверка публичных сообщений существующим read-only
Telethon-транспортом:

```bash
python -m app.historical_telegram_community_audit \
  --product-id 52d7e59e-5ac5-4363-b829-c93e33e48272 \
  --max-groups 12
```

Единоразовый workflow `.github/workflows/femdom-historical-community-audit.yml`
запускается **только при добавлении/изменении самого workflow в main**.
Он ждёт развёртывания именно проверяемого коммита, читает старую
продуктовую базу внутри production API, ограниченно проверяет
сохранённые публичные группы и загружает закрытый диагностический JSON
как GitHub Actions artifact сроком на семь дней. Выводит в job log
только обезличенное summary.

Если research-сессия отсутствует, находится в FloodWait или новый
release не развернулся, результаты будут честно обозначены как
`RESEARCH_CONNECTOR_UNAVAILABLE`, `DEFERRED_FLOOD_WAIT` или
ошибка workflow. Никакие кандидаты не считаются «проверенными» по
старому снапшоту вместо реального чтения.

## Что точно НЕ делаем

- Не ищем новые группы платным или бесплатным глобальным поиском.
- Не вступаем в группы, не пишем сообщения, не публикуем сторис,
  не обновляем профиль и не меняем режим одобрения.
- Не читаем списки участников и личные сообщения.
- Не записываем никакого прогресса в RuntimeStateStore.
- Не объявляем keyword-попадание реальной конверсией.
